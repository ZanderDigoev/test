# Как программа разговаривает с автомобилем

Короткая справка по внутреннему устройству — пригодится, если понадобится
что-то дописать.

## Слои

```
   CLI  ──►  ObdSession / UdsClient  ──►  Elm327  ──►  Transport  ──►  адаптер
                      │                     │
                      └── framing.py ◄──────┘
```

* `Transport` — байты туда-обратно, ничего не знает о протоколе.
* `Elm327` — AT-команды, выбор протокола, физическая адресация.
* `framing` — превращает напечатанные адаптером строки в сообщения блоков.
* `ObdSession` / `UdsClient` — сервисы: чтение ошибок, параметров, ячеек памяти.

## Настройка адаптера

При открытии соединения выполняется:

| Команда | Зачем |
| --- | --- |
| `ATZ` | полный сброс адаптера |
| `ATE0` | выключить эхо — иначе каждый запрос возвращается обратно |
| `ATL0`, `ATS0` | убрать переводы строк и пробелы, чтобы разбор был предсказуем |
| `ATH1` | **показывать заголовки** — без них не понять, какой блок ответил |
| `ATAT1` | адаптивные тайминги |
| `ATSP0` | автоопределение протокола |
| `ATDPN` | узнать, какой протокол в итоге установился |

Заголовки включаются намеренно. На запрос без явного адреса отвечают
несколько блоков сразу, и без заголовка их ответы сливаются в кашу.

## Разбор ответов

### CAN (ISO 15765-4)

Строка выглядит как `7E8064100BE3EA813`: три ниббла адреса, затем кадр
ISO-TP. Первый ниббл кадра задаёт его тип:

| Ниббл | Тип кадра | Что делает `framing` |
| --- | --- | --- |
| `0` | одиночный | длина в младшем ниббле, дальше данные |
| `1` | первый из многих | длина 12 бит, начинает сборку |
| `2` | продолжение | дописывает в буфер по порядковому номеру |
| `3` | управление потоком | пропускается, его шлёт сам адаптер |

Набивка до восьми байт отбрасывается по заявленной длине.

Обрати внимание: при 11-битном адресе строка целиком имеет **нечётную**
длину (три ниббла заголовка). Проверять её на чётность нельзя — это
частая ошибка в разборщиках.

### K-line (ISO 9141-2, ISO 14230-4)

Строка выглядит как `486B104100BE3EA813BB`: три байта заголовка, данные и
контрольная сумма — восьмибитная сумма предыдущих байт. `framing`
отбрасывает сумму, если она сходится либо если длина совпадает с заявленной
в байте формата; иначе оставляет байт на месте, чтобы не съесть данные.

Каждая строка — отдельное сообщение. Длинные ответы режима 09 приходят
несколькими сообщениями, в каждом повторяется `49 <PID> <номер>`.

## Различия шин, которые пришлось учесть

| Что | CAN | K-line |
| --- | --- | --- |
| Ответ режима 03 | `43 <число кодов> <коды>` | `43 <коды>`, по три кода в сообщении |
| VIN (режим 09) | одно сообщение ISO-TP | пять сообщений по четыре байта |
| Адрес блока | `7E8`, `748`, … | `10`, `40`, … |
| Расширенная диагностика | UDS с адресацией `ATSH` | не реализована |

## Расширенная диагностика

`UdsClient` — менеджер контекста. На входе выставляется физическая
адресация (`ATSH`, `ATCRA`, кадр управления потоком), на выходе она
**обязательно** возвращается к стандартной: иначе следующий обычный запрос
OBD-II уйдёт не тому блоку.

Отрицательный ответ `0x78` («ответ готовится») ошибкой не считается — блок
просит подождать. Адаптер к этому моменту уже вернул приглашение, поэтому
запрос повторяется до трёх раз; все используемые сервисы идемпотентны.

Молчание блока и отказ блока — разные вещи: первое означает «блока нет»
(`UdsNoResponse`), второе — «блок есть, но не может». На этом различии
построен поиск блоков на шине.

## Симулятор

`avensis/simulator.py` изображает адаптер и автомобиль. Профили:

| Профиль | Шина |
| --- | --- |
| `avensis_t25` | CAN, 11 бит, 500 кбит/с |
| `avensis_t25_kline` | ISO 9141-2 |

```bash
avensis --port 'sim://?profile=avensis_t25_kline' scan
```

Виртуальная машина отдаёт VIN `SB1BJ56L20E095222`, коды `P0301`, `P1349`,
`P0420`, неподтверждённый `P0171`, постоянный `P0420`, ошибку `C1336` в
блоке ABS и три настраиваемые ячейки в кузовном блоке.
